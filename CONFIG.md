# Карта настроек

Четыре уровня, по времени жизни значения. Чем ниже в таблице — тем чаще меняется.

| где | что | пример |
|---|---|---|
| `.env` (в `.gitignore`) | секреты | `ANTHROPIC_API_KEY` |
| `config/tuning.json` | поведение системы: пороги, веса, лимиты | `saturation`, `speakWeights` |
| `user/profile.json` | описание пользователя | `knownZipf` |
| аргументы команды | параметры одного запуска | `--limit 30` |

Приоритет: аргументы → файл конфига → умолчания в `src/config.ts`.

## `user/profile.json`

Описывает **пользователя**, а не систему. Отдельно от `tuning.json`, потому что
у разных людей значения разные, а пороги скоринга — общие.

| ключ | умолчание | что делает |
|---|---|---|
| `knownZipf` | `4.0` | выше этой частотности слово считается известным и не предлагается |
| `recordZipf` | `6.0` | выше этого слово вообще не пишется в словарь (служебный каркас: `the`, `and`) |
| `dailyNew.speak` | `5` | подсказка по лимиту новых карточек в день (в Noji выставляется вручную) |
| `dailyNew.read` | `15` | то же для колоды на узнавание |

**Про `knownZipf`.** Значение 4.0 получено калибровкой: слова уровня
`delicate, gently, steadily` (около 4.0) знакомы, `timid, ordeal, humility`
(около 3.5) — нет. Граница легла между ними. Понижай по мере роста уровня.

**Почему `recordZipf` выше `knownZipf`.** Между ними лежит запас: слова
пишутся в словарь, но не предлагаются. Без этого поднять `knownZipf` через год
будет нечем — счётчиков по ним никто не собирал, а книги могут быть недоступны.

## `config/tuning.json`

### `contexts` — примеры предложений из книги

| ключ | умолчание | что делает |
|---|---|---|
| `maxStored` | `10` | сколько примеров сохранять на лемму |
| `minLength` | `25` | короче — не сохраняем (обрывки реплик) |
| `maxShown` | `3` | сколько показывать при отборе |

`maxStored` больше `maxShown` намеренно: глазами читаются три, а модели при
группировке по значениям нужно больше — пропущенное второе значение потом
ничем не восстановить. Выборка равномерная по тексту, не первые N: у 36% лемм
вхождений больше трёх, и первые три покрывают лишь 39% диапазона слова.

### `scoring` — отбор кандидатов

| ключ | умолчание | что делает |
|---|---|---|
| `floorZipf` | `2.0` | ниже этой частотности слово в жизни не встретится, `lifeValue` = 0 |
| `saturation` | `40` | столько вхождений в книге дают максимальный `bookValue` |
| `historyOverride` | `3` | со стольких книг слово предлагается вопреки `knownZipf` |
| `speakThreshold` | `0.5` | `lifeValue` выше — маршрут в speak, ниже — в read |
| `checkSenseRatio` | `50` | во сколько раз выше ожидаемого, чтобы пометить «проверь значение» |
| `speakWeights` | `life 0.7 / book 0.3` | вес осей в приоритете внутри speak |
| `readWeights` | `life 0.2 / book 0.8` | то же для read |

**Две оси не складываются в одну.** `bookValue` — польза для чтения этой книги
(слово, встреченное 48 раз, экономит 48 спотыканий). `lifeValue` — польза
вообще, и она **не растёт монотонно с редкостью**: максимум у границы
`knownZipf`, спад к нулю в сторону экзотики.

**`historyOverride`.** Слово выше порога, попавшееся в трёх книгах, порог
обходит: в твоём круге чтения оно частотнее, чем в корпусе wordfreq
(собранном из веба и субтитров). Свидетельство из собственного чтения сильнее
глобальной статистики.

**`checkSenseRatio` — пометка, а не решение.** Ловит и настоящие ловушки
(`dolphin` у Хемингуэя — корифена, `stern` — корма), и просто тематически
частотное (`breeze`, `turtle`). Различить статистикой нельзя, поэтому маршрут
не меняется, а рядом с контекстами появляется предупреждение.

### `review` — сколько показывать при отборе

| ключ | умолчание | что делает |
|---|---|---|
| `topSpeak` | `30` | сколько speak-кандидатов показать |
| `topRead` | `15` | сколько read-кандидатов |

Раздельно, а не общим числом. Формулы приоритета у колод разные, и общий топ
даёт перекос: на реальной книге топ-40 состоял из 37 speak и 3 read, за бортом
остались `skiff` ×48, `oar` ×25, `harpoon` ×20.

### `generation` — карточки

| ключ | умолчание | что делает |
|---|---|---|
| `model` | `claude-sonnet-4-6` | модель |
| `maxTokens` | `2000` | потолок ответа |
| `maxAttempts` | `3` | попыток на карточку, не прошедшую проверки |
| `defaultLimit` | `10` | слов за прогон, если не задан `--limit` |

**Про стоимость.** Чистая speak-карточка — 2 запроса (генерация плюс проверка
на неоднозначность). С двумя переделками — 6. read-карточки дешёвые: один
запрос, проверка на неоднозначность им не нужна.

| команда | флаг | по умолчанию |

## Промпты — `prompts/*.md`

| файл | роль |
|---|---|
| `speak-cards.md` | системный: cloze для активного словаря |
| `read-cards.md` | системный: слово → перевод для узнавания |
| `fix-card.md` | системный: переделка карточки, не прошедшей проверку |
| `fill-blank.md` | системный: заполнение пропуска вслепую |
| `user-word.md` | шаблон: слово + контексты |
| `user-fix.md` | шаблон: прежняя версия + причина отказа |

Подстановка `{{key}}` через `src/prompts.ts`. Незаполненный плейсхолдер бросает
ошибку, а не уезжает в модель молча.

**Markdown, а не JSON:** многострочный текст в JSON превращается в
`"строка\nстрока"`, комментариев нет, а diff бесполезен — правка одного слова
помечает всю строку изменённой.

**Обёртка в TypeScript нужна потому, что промпт и парсер связаны контрактом.**
Промпт требует ответа вида `[{"sense":…, "front":…}]`, тип `RawCard`
в `generate.ts` его разбирает. Меняешь одно — обязан менять другое.

## Что НЕ настраивается и почему

**Проверки валидатора.** Утечка ответа, когнат, неоднозначность, соответствие
буквы пропуска — не отключаются. Карточку из Noji нельзя ни исправить, ни
удалить, поэтому любая ошибка вечная.

**Длина пропуска.** Не проверяется, а исправляется арифметикой: модели плохо
считают символы, и жечь на этом попытки перегенерации бессмысленно.

**Порядок записи при экспорте.** Сначала журнал, потом статусы. Сбой между ними
приводит к безопасному повтору; обратный порядок дал бы `accepted` без файла,
то есть слово молча пропало бы навсегда.
